# Settings Panel Mockups — B1/B2/B3 Notes

**B1 — Sidebar nav rail (macOS System Settings style).** A fixed 200px left rail lists category anchors (Performance / Export / Memory / Shortcuts); the right pane scrolls through all four sections top-to-bottom, with the rail's active item acting as a jump-link/scroll-position indicator rather than a hard tab switch. Trade-off: most visually consistent with a "real settings app" mental model and scales well if more categories are added later, but the rail eats ~200px of the 880px dialog width, leaving the content column noticeably narrower than B2/B3 — fine for single-column controls (sliders, tier cards) but tight for the two-column shortcut list, which had to drop to a single column here.

**B2 — Single continuous scroll, two-column grid.** No navigation chrome at all: one scrollpane with section-label dividers (reusing the rename-dialog's `renameSectionLabel` pattern) and a responsive 2-column grid for compact sections (Parallelism, Export) that widen to full-bleed for larger ones (Memory tiers, Shortcuts). Trade-off: zero clicks to see everything, lowest cognitive overhead for a panel this small, but a taller/denser page than B1/B3 — everything is visible immediately but there's more to visually parse in one glance, and it doesn't scale gracefully if the settings list grows much beyond four sections.

**B3 — Top segmented tabs + persistent summary rail.** A macOS-style segmented control (Performance / Memory / Shortcuts) sits under the header, and a slim 220px right-hand "at a glance" rail permanently shows the four current values (decode lanes, export quality, retention tier + budget, shortcut conflict count) regardless of which tab is active — so the user never loses sight of the whole configuration while drilling into one area. For this mockup all four settings are rendered in the main content column (matching the acceptance requirement to show everything statically) with a comment marking which section belongs to which tab. Trade-off: the summary rail is the most novel/differentiated idea of the three and adds real "glanceability," but it's also the most complex layout to implement correctly in Flutter (three independent scroll-affecting regions) and the rail's real-estate cost is similar to B1's nav rail, for a different purpose.

All three use `HalcyonTokens.dark` values verbatim: dialog `#383838`, pane `#333333`, surface `#414141`, input `#262626`, border `#515151`, borderSoft `#454545`, text `#E0E0E0`/`#9A9A9A`/`#6F6F6F`, accent `#0A84FF`, danger `#FF453A` (used for the shared "X" key conflict state). Dialog size is 880×540 to match `RenameDialog`. Retention tier numbers (224/304/384 MB, -3/+5, -3/+8, -3/+11) come directly from `retention_policy.dart:67-82`; export quality default is 90 per `photo_export_service.dart`; the 7 shortcuts and their current key bindings come from `main_screen.dart:104-128`.

Note: the `ui-ux-pro-max` Skill tool ran successfully (queried for desktop settings-panel UX patterns) and its guidance (segmented controls / sidebar nav as standard desktop settings patterns, monospace for numeric captions, section dividers, 4.5:1 contrast) informed all three variants; no fallback was needed.
