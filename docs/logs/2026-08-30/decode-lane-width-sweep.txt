METHOD (Sec 9.2 of spec-parallel-decode-lane.md, verbatim):
  * Fixed corpus: local_data/photo_samples/DNG, fixed MAX_SAMPLES, same
    machine, same HEAD, all runs back-to-back.
  * Sweep width in {1, 2, 3, ceiling}; report wall-clock seconds for the
    whole batch and user+sys CPU seconds for each.
  * Speedup(w) = wall(1) / wall(w).
  * Every run captures its own exit code inside the artifact with RC=$? on
    the line immediately after the command (never ${PIPESTATUS[0]}, never a
    harness-reported code).
  * The artifact records the git HEAD hash and is checked to be equal to
    the delivered tip.
  * Long runs (>30s) are split into smaller MAX_SAMPLES batches rather than
    backgrounded, exactly as the 2026-08-30 measurement did
    (decode-cpu-parallelism.txt:76-83).

VERDICT RULE (Sec 9.3 of spec-parallel-decode-lane.md, verbatim):
  * Speedup(3) >= 1.8 -> keep kDefaultLaneWidth = 3.
  * 1.3 <= Speedup(3) < 1.8 -> set kDefaultLaneWidth = 2 and record why.
  * Speedup(3) < 1.3 -> set kDefaultLaneWidth = 1; the setting stays
    shipped (the user asked for it) but stops being on by default, and the
    number goes in the memory.md entry.
  * If Speedup(w) < Speedup(w-1) for any w (contention regression), the
    ceiling for that rung is lowered to w-1.
  * Re-running with different parameters until a favourable number appears
    is forbidden. The first clean run under the above method decides.

================================================================================
VERDICT
================================================================================

Speedup(3) = 1.167, which is < 1.3.
Per the pre-registered verdict rule (Sec 9.3): Speedup(3) < 1.3 -> set
kDefaultDecodeLaneWidth = 1. The setting stays shipped (the user asked for
it, and DecodeLane does still admit multiple concurrent decodes when the
user raises the slider), but it stops being on by default.

No re-run was performed to seek a more favourable number; this is the first
and only clean run under the pre-registered method.

Contention-regression sub-rule: Speedup(2) = 0.935 < 1.0 (worse than
sequential), and Speedup(w) is non-monotonic across the sweep (2 < 1 < 5 <
3 in wall-clock terms) rather than climbing with width. On a 28-core / 256
GiB machine with the memory-rung ceiling at 5 and the CPU ceiling also at
5, this indicates the bottleneck for this corpus/machine combination is not
memory or CPU count but something else in the decode path that does not
parallelise across concurrent worker isolates for this sample size (most
likely the single shared Metal GPU backend the pipeline reports at startup
-- `[Pipeline] GPU backend: metal` -- serialising the actual decode/process
stage regardless of how many isolates request it, and/or per-isolate
`DynamicLibrary.load()` + pipeline cold-start overhead dominating a
12-sample batch). This is consistent with -- not a contradiction of -- the
kDefaultDecodeLaneWidth=1 verdict above: whatever the root cause, extra
concurrent decode requests are not paying for themselves on this
measurement, so the shipped default should not ask for them.

The formal "ceiling for that rung is lowered to w-1" contention-regression
clause is stated in terms of the width sweep points {1,2,3,ceiling}, not
the separate memory/CPU ceiling rungs in retention_policy.dart; the
practical effect of applying it here is identical to the primary verdict:
the shipped DEFAULT drops to 1. The `laneCeilingFor` MAXIMUM (still 5 on
this machine) is left untouched by this task -- lowering the hard ceiling
itself is out of Task 7's owned-file scope (kDefaultDecodeLaneWidth is the
only constant this task is authorised to change) and is noted below as an
open question for the team-lead / user, not applied unilaterally.
